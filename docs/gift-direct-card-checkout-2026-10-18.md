# خرید هدیه و کارت‌به‌کارت مستقیم — راهنمای انتشار

## رفتار کاربر

- در «انتخاب روش پرداخت»، کاربر «💳 کارت‌به‌کارت» را می‌زند و **مستقیم** وارد نمایش مبلغ، شماره کارت، بانک و نام دارنده کارت پیش‌فرض فعال می‌شود. بانک مقصد از نخستین رکورد فعال با `display_order` کمتر انتخاب می‌شود؛ هیچ اطلاعات بانکی در کد ثابت نیست.
- دکمه «خرید برای دیگری» دیگر یوزرنیم نمی‌گیرد؛ سفارش از نوع `gift` ساخته می‌شود. پس از **پرداخت کامل تأییدشده**، یک لینک `https://t.me/<bot_username>?start=gift_<token>` برای خریدار ارسال می‌شود. توکن تصادفی ۳۲ کاراکتری و یک‌بارمصرف است.
- تاریخ انقضا از زمان **تأیید پرداخت** و براساس `Brand.gift_expiry_hours` است؛ پیش‌فرض ۷۲ ساعت، مجاز ۱ تا ۷۲۰ ساعت.
- صرف پرداخت هدیه باعث ساخت اشتراک نزد سرویس‌دهنده نمی‌شود. اولین کاربر معتبر که پیش از انقضا لینک را باز کند، صاحب هدیه می‌شود و فعال‌سازی پس از Claim اجرا می‌شود.
- کاربر **قدیمی**: فقط هدیه را دریافت می‌کند؛ هیچ دعوت/امتیاز معرفی جدید ایجاد نمی‌شود. کاربر **واقعاً جدید**: هم هدیه دریافت می‌کند و هم به‌عنوان دعوت جدیدِ خریدار ثبت می‌شود. امتیاز خرید هدیه نیز تنها در صورت جدیدبودن گیرنده قابل بررسی است. کاربر از دعوت/پاداش دیگران بازنویسی نمی‌شود.
- در صورت نبود سرویس‌دهنده فعال، Claim ناموفق می‌ماند و توکن مصرف نمی‌شود. کدهای منقضی، استفاده‌شده و تلاش خریدار برای دریافت هدیه خودش رد می‌شوند.
- وقتی کسی تا پایان اعتبار لینک آن را استفاده نکند، اشتراکی فعال نمی‌شود. موضوع بازپرداخت/جایگزینی هدیه باید جداگانه در سیاست تجاری تعیین شود؛ این Patch بازپرداخت خودکار ندارد.

## کجا تنظیم کنیم؟

- **Brands → Brand**: نام کاربری ربات و `gift_expiry_hours` (مثلاً 72)
- **Orders → Payment cards**: کارت‌های مقصد، ترتیب، فعال/غیرفعال، `unique_amount_enabled`, `unique_amount_max_extra`
- **Orders → Gift vouchers**: کدهای صادرشده، لینک، انقضا، گیرنده و وضعیت عضویت جدید
- **Orders → Card transfer quotes**: مبلغ پایه، مبلغ اختصاصی، کارت و زمان اعتبار

## مبلغ یکتا و محدودیت تأیید خودکار

- به‌طور پیش‌فرض `unique_amount_enabled=False` است و مبلغ نمایش‌داده‌شده دقیقاً مبلغ سفارش است.
- پس از فعال‌کردن این گزینه برای یک کارت، اگر مبلغ سفارش **تومان** باشد بازه ۱ تا ۹۹ تومان (قابل محدودسازی در ادمین) برای واریز تخصیص داده می‌شود؛ مثلاً ۵۰۰٬۰۰۰ → ۵۰۰٬۰۰۱. تخصیص با `select_for_update` روی کارت و قید یکتایی دیتابیس انجام می‌شود. برای ارز ریال گام‌های ۱۰ ریالی استفاده می‌شود. ارزهای دیگر در حالت فعال بودن مبلغ یکتا رد می‌شوند تا پرداخت اشتباه ثبت نشود.
- رزرو هر مبلغ برای ۷ روز نگه داشته می‌شود تا واریزی دیرهنگام با سفارش جدید اشتباه نشود. اگر در قیمت معین تمام شناسه‌ها رزرو شده باشند، خرید با پیام مناسب متوقف می‌شود؛ هیچ شناسه‌ای تکرار نمی‌شود.
- **تطبیق پیامک ≠ تأیید بانکی.** صرف پیدا شدن مبلغ خاص در SMS، حق تأیید خودکار پرداخت، تغییر وضعیت Order یا فعال‌سازی اشتراک ایجاد نمی‌کند. API دریافت و اعتبارسنجی مستقل گردش حساب در این تغییر اضافه نشده است؛ دریافت و تأیید رسید همچنان دستی است. بعداً می‌توان جریان مطمئن بانک را به مدل `CardTransferQuote` وصل کرد.
- اختلاف مبلغ در `Payment.amount` ذخیره می‌شود، ولی `Order.final_price` همان قیمت محصول است؛ امتیاز خرید نباید با اختلاف جزئی محاسبه شود.

## مهاجرت و تست قبل از Production

```bash
uv sync --frozen
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run python manage.py migrate --plan
uv run python manage.py migrate
uv run python manage.py test apps.orders.test_checkout_links apps.bot.tests apps.referrals.tests apps.orders.tests
```

موارد دستی ضروری روی Staging: خرید کارت‌به‌کارت واقعی بدون منوی انتخاب بانک، ذخیره رسید، تأیید پرداخت، پیام لینک به خریدار، Claim توسط گیرنده قدیمی و جدید، دوبار استفاده از توکن، انقضا، چند سفارش هم‌مبلغ هم‌زمان، و خاموش‌بودن سرویس‌دهنده در لحظه Claim.

این بسته بر پایه ZIP `totnet-regression-reconciliation-2026-10-17.zip` است. اگر روی پروژه محلی خود تغییرات دیگری داده‌اید یا `.rej` باقی مانده، نخست `git apply --check` را اجرا کنید و **بدون بررسی ادغام، فایل‌ها را overwrite نکنید**.
